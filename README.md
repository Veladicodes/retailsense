# RetailSense Enterprise

End-to-end weekly retail demand forecasting: **Python + SQL**, 67 leak-free features, XGBoost / LightGBM /
Random-Forest / Ridge configurations and ensembles, **Apache Airflow** orchestration, **S3** (MinIO locally),
**Docker**, and a **Streamlit** dashboard.

Data: [UCI Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii) (CC BY 4.0) - 1,055,289
cleaned transaction lines, Dec 2009 - Dec 2011, forecast at SKU x week for the 100 highest-volume SKUs.

## Measured results (holdout: 13 weeks, 2011-09-05 to 2011-11-28, never used for training or selection)

| Metric | Best baseline (`ewm_03`) | Selected model (`ensemble_top3`) |
|---|---|---|
| SKU-week MAPE | 108.0% | 85.3% |
| SKU-level WAPE | 52.9% | 48.7% |
| Weekly **total** demand MAPE | 14.2% | 19.8% |

Full table for all 23 configurations + 4 baselines: [`reports/experiments.md`](reports/experiments.md)
(regenerated by `make experiments`; `tests/test_phase5_deploy.py` fails if this README drifts from `reports/summary.json`).

### What these numbers do and do not say

- The models beat the best naive baseline **at the SKU level** (WAPE 52.9% -> 48.7%, MAPE 108.0% -> 85.3%).
- Per-SKU weekly demand in this wholesale dataset is very lumpy, so SKU-level MAPE stays high for every method
  (it is dominated by weeks with tiny actual demand). WAPE is the more meaningful metric here.
- At the **total weekly demand** level a plain exponentially-weighted average (14.2%) is *better* than the
  selected model (19.8%). Sums of median-style SKU forecasts under-forecast the aggregate.
- There is a single 13-week holdout, so small differences between models are within noise.

## Architecture

```
raw CSV/XLSX --ingest--> SQL (raw_sales, calendar_weeks) --weekly_panel.sql--> features (67) --> model grid
   Airflow DAG: ingest -> validate -> build_features -> train -> forecast -> publish_s3
   outputs: SQL (model_runs, forecasts) + S3 runs/<date>/{experiments.md, summary.json, next_week_forecast.csv}
   Streamlit reads only SQL
```

| Claim | Where |
|---|---|
| Python + SQL | `sql/schema.sql`, `sql/weekly_panel.sql` (aggregation, zero-filled SKU x week panel, top-N selection), `sql/split_weeks.sql` |
| 67 features | `retailsense/features/registry.py` - asserted unique and leak-free (perturbing week *t* sales must not change any week-*t* feature) |
| 15+ configurations | `retailsense/models/grid.py`: 22 configs (XGBoost 9, LightGBM 9, Random Forest 2, Ridge 2) + top-3 ensemble, plus 4 baselines |
| Honest evaluation | `retailsense/models/experiment.py`: select on validation, refit on train+val, score the holdout once |
| Airflow + S3 | `dags/retailsense_weekly.py`, `retailsense/storage/s3.py` |
| Docker | `Dockerfile`, `docker/airflow.Dockerfile`, `docker-compose.yml` |
| Streamlit | `app/streamlit_app.py` |

## Run it

```bash
pip install -r requirements-dev.txt
make data          # downloads UCI Online Retail II -> data/raw/online_retail_ii.csv
make experiments   # SQLite + local run, regenerates reports/
make test          # pytest with coverage
make demo          # experiments + Streamlit
```

### Docker stack

```bash
make data          # the DAG's ingest task reads data/raw/online_retail_ii.csv
make up            # Postgres + MinIO (S3) + Airflow + Streamlit
```

Then open Airflow at http://localhost:8080 (admin / admin), unpause `retailsense_weekly` and trigger it.
Artifacts are published to MinIO at http://localhost:9001 (minioadmin / minioadmin) under `runs/<date>/`, and the
dashboard at http://localhost:8501 picks up the results from Postgres.

The test-suite runs against SQLite with S3 mocked (moto) and is also run under Airflow 2.9's pinned libraries
(pandas 2.1.4, SQLAlchemy 1.4.52, numpy 1.26.4).

## Repository layout
